The check finds filler the house voice rules out, an en dash used as a dash, a placeholder left in and an emoji. It also reads `.jsx` files and finds more semicolons joining clauses, so a repository that moves to this version may find lines written before it.

- **Rules.** A trailing -ing clause, an inflated word, an empty opener, a canned closer, a wordy phrase, an intensifier, a leftover placeholder, an en dash used as a dash and an emoji are each a rule of their own, with words that have a technical meaning in code or docs, such as `harness` and `dynamic`, left out. A stock phrase such as `in summary` counts only where it opens a sentence with a comma. A semicolon after a digit, a closing bracket or a quote with more on the line joins clauses as one after a letter does. `.jsx` files are read. Code quoted in backticks in a comment and a doc comment's example are left out, and so are a page's code samples, as Markdown's inline code is. A numeric character reference such as `&#169;` reads as no text, and a Markdown reference whose label the file defines reads as a link.
- **Command.** A passing run says every file it read follows every rule, rather than naming the rules.
- **Docs.** The README lists every rule with an example, says what it reads in each kind of file, shows a failure as text, covers CI with the Node it needs, a pre-commit hook and every export, and opens with the kit's badges and links. The package's description names the new rules.
- **Tests.** Each new rule finds the lines it names and passes the lines that only look like them. A semicolon after a digit, a bracket or a quote is found while code quoted in a comment, a commented-out statement, a doc comment's example, a page's code sample and a character reference are not. A doc comment's bracketed parameter and a defined Markdown reference are not read as placeholders.
